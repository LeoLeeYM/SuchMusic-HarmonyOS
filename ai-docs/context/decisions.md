# 技术决策记录

## 2026-10-24：建议优先验证混合架构（尚未实施）

方案：保留 Vue 移动界面，使用 ArkWeb 和鸿蒙原生桥接，普通播放由原生内核承担。

原因：已有手机页面、业务逻辑及移动 IPC 契约可复用，主要平台差异集中在播放、文件、网络和生命周期。

未选仅 Web 包装作为正式默认方案：后台队列、Web 生命周期和高级音效尚未经鸿蒙验证。未选全 ArkUI 重写作为首版：模板、样式、动画和动态插件宿主重写成本明显更高。

优点：保留现有交互，原生播控边界明确。缺点：需维护 Web/原生两层及事件同步；高级 DSP 仍需专门实现。

未来影响：平台接口须显式区分 Android/HarmonyOS；原生播放状态与后台队列应独立于页面渲染。若技术验证未通过或原生体验成为硬目标，重新评估边界与工期。

决策状态：评估建议，不代表用户已经授权开发、发布或改变现有架构。


## 2026-10-24：实施 ArkWeb + 原生媒体内核体验版

用户明确授权尝试移植并提供真机，采用上述混合架构。相比全 ArkUI 重写，复用已有手机页面及插件接口能更快验证关键风险；相比纯 Web 音频，AVPlayer/AVSession 可接入系统播控及后台音频任务。

- ArkWeb 本地资源使用稳定 HTTPS 来源并原生拦截：rawfile 的 null origin 无法可靠加载 ES modules；WASM 必须返回精确 application/wasm，不附文本 charset。代价是维护 MIME 映射和导航白名单。
- Capacitor 兼容桥接仅在 harmonyos 构建注入：保留 Android/桌面原路径，避免双端大面积改动；代价是要维护插件方法表。
- 首版暂不实现 DSP/跨应用悬浮歌词，并给出 UI 提示：当前 AVPlayer 没有复用 WebAudio 音效图，不能让无效开关伪装生效。未来可补原生 DSP 或单独音频渲染管线。
- 文件通过系统选择器复制进沙箱：不申请广泛共享存储权限，不依赖短期 URI 长期有效；代价是占用额外空间、同名需重命名、大文件需后续流式处理。
- 原生媒体会话为唯一系统播控来源：禁用 HarmonyOS 浏览器 MediaSession，防止竞争。队列仍在 Vue，短时验证通过不代表长期后台可靠，未来应下沉原生。
- Hvigor 构建使用纯 ASCII 缓存目录：不移动或改名用户中文源码目录；代价是构建需同步资源，签名仅留本机缓存。

架构影响：新增 ArkTS 工程与异步原生契约；不更改服务端 API/数据库，不承诺 APK 与 HAP 功能完全等价。


## 2026-10-24：系统栏背景延伸、交互内容单独避让

首版保留原生系统栏避让造成顶部和底部白条。采用全屏窗口+透明系统栏，让页面背景绘制到底；只对按钮和文字应用原生安全区。没有采用隐藏状态栏/手势条的方案，以保留正常系统信息与导航。

安全区使用 Window AvoidArea 实测值并转换为 CSS 像素，不写死机型高度或直接套用 vp；优势是适应密度与旋转变化，代价是维护原生监听及 Web 同步。在页面首次加载和尺寸变化时重新同步，避免只在初始化注入一次。播放页独立覆盖图标明暗，避免浅色主题下深色播放器顶部图标不可读。

## 2026-10-24：以完整播控区域为单位原生化（已撤销）

用户授权执行原生化并要求 UI 好看。选择 ArkUI 整块底部播控、全屏播放页和队列，复用现有 Web 首页、搜索、歌词、评论及插件。这样能让播放/暂停/seek 直接操作 AVPlayer，又保持原有业务可达；代价是维护明确的界面切换、触摸分发和状态契约。

没有把每个 Web 按钮单独同层替换：大量坐标/滚动/手势同步会增加复杂度。没有同时重写所有歌词/插件页面：它们涉及较多已有行为，需要独立验收。原生界面使用封面派生背景、深色遮罩和明确文字层次，底栏跟随系统应用主题。

队列先下沉执行和选曲，本地文件及已知路径可原生切歌；音源插件暂保留 Web 解析，持久化继续复用原格式。优势是逐步增强后台可靠性而不迁移用户数据；限制是未解析在线源及重启恢复仍依赖 Web。未来独立原生持久化与插件执行环境应另设迁移和回滚方案。

## 2026-10-24：按用户要求撤销播控原生化

用户要求撤销原生化，因此恢复原生化前的 Web 底栏、播放页和 Web 队列控制。保留已完成的鸿蒙混合移植、AVPlayer/AVSession、系统栏沉浸和系统播控封面修复。没有回退整个 Git 工作区，因为其中包含用户既有修改及独立修复；采用 20:44:05 源码快照定点恢复，并保存撤销前快照。

优势是恢复原来的统一界面与交互，减少 Web/ArkUI 双套播控状态同步；代价是队列控制再次依赖 Web，原生队列的后台独立执行能力不再存在。未来如重新推进原生 UI/队列，应作为独立任务重新确认范围，不将历史原生验收结果视为当前能力。用户存储格式、包名、签名和本地资源来源均保持不变。

## 2026-10-24：复用本地算法实现逐字歌词

沿用项目已有 V3/V4 Worker 与增强 LRC 存储，修复移动端服务生命周期和 DOM 高亮同步，不新增远程 AI 服务或原生歌词页。原因是用户刚撤销原生 UI，现有算法已能在鸿蒙真实 MP3 上完成解码、对齐、保存；主要缺口是自动触发、恢复和渲染衔接。优势是离线、无新增依赖且保留原视觉风格；限制是估算时间精度不等于人工标注，大文件与长时间后台生成仍需专测。未来可接入真实逐字源，但不将普通歌词简单均分冒充官方时间戳。

## 2026-10-24：逐字歌词先复用，自动生成静默运行

用户反馈每首生成久且提示打断，改为已有缓存优先、音源 YRC 次之、无数据才后台生成。没有简单均分字时长或删减算法换取表面速度，避免降低对齐质量；不承诺无源数据的新歌首次分析变成瞬时。自动流程统一不暂停、不弹提示，手动任务保留反馈。旧 genMode 仅保留数据兼容，不再控制自动阻塞行为。

缓存跨音质复用限应用管理的 online-cache 和明确 source/id 文件名，本地路径保持独立，避免同名文件错误共用。保留旧清单 key，串行提交清单以避免并发覆盖；未来扩展更多音源应沿用明确身份与短超时，不引入模糊歌名匹配。

## 2026-10-27：独立鸿蒙仓库采用当前源码快照

目标仓库只有 README 和 MIT 初始化模板，选择基于该提交追加当前可构建源码，不重写远端历史，也不导入未审计的旧仓库历史。保留原项目/Android 作者署名并以源项目 AGPL-3.0 替换初始化许可证。保留共用 Vue、歌词包、Android/Electron 源码，避免为了仓库命名拆散现有依赖；可选桌面预编译解码器不作为鸿蒙源码发布内容。

硬编码 AI 服务凭证改为可选本机 VITE_SPARK_API_KEY，缺失时明确报错；本机旧值保留于忽略的 .env.local，避免破坏个人开发配置。环境变量可解除源码与个人账号绑定，但 VITE 值仍会进入客户端包，因此共享构建不得配置个人凭证。没有新增服务端代理或修改鉴权协议。

优点是源码边界清晰、远端原提交可追溯、无需复制签名；代价是新维护者需自行准备 SDK、签名及可选 AI 配置。后续改动应基于目标仓库正常提交，禁止用强推覆盖其他人的更新。
